初探#

很常规的两个路径：

apk\lib\arm64-v8a\libil2cpp.so

.apk\assets\bin\Data\Managed\Metadata\global-metadata.dat 但有加密。

魔数头被抹掉，可以看到大量的 0x66，有明显的统计特征，0x00 占比 20.477%20.477\%20.477%，0x66 占比 7.175%7.175\%7.175%，0x99 占比 1.868%1.868\%1.868%

直接怀疑是固定密钥 xor 或 sub，进一步猜测是纯 xor，但部分区段是不符合明显 0x66 的特征，猜测是按区块的异或解密。

此外，0x1000-0x4FFF 区间的统计熵显著变大。

推测这段有单独的 Key 或 AES 等加密算法。

恢复流程#

整体恢复顺序如下，后文再展开各处的逆向分析：

  1. 获取用于解密 libil2cpp.so 的 seed。
  2. 使用 seed，按区域配置解密 libil2cpp.so。
  3. 分析解密后的 libil2cpp.so，结合 libanort.so 追踪 global-metadata.dat 的加载与解密逻辑，并解密 metadata。
  4. 将解密后的 libil2cpp.so 和 global-metadata.dat 一起交给适配后的 Il2CppDumper 导出。

代码段解密#

查看 0x1CBC2C，往后 0x10 就是 libil2cpp.so，后面还有 .rodata、.text 等区域记录。拿 .text 这条举例：

sub_AF8C0 读取配置，在 0xB0820 调用 sub_13FEE0，模式 1 继续到 sub_13E57C。

这条记录的处理方式是：

  1. 跳过 0x2000 - (起点 & 0xFFF) 字节，得到 0x4D85000。
  2. 从这里开始，前 0x4000 字节分为八个 0x800 字节块，进行 AES 处理。
  3. 从 0x4D95000 开始调用 sub_156870，每个完整 0x10000 字节块的前 0x4000 字节做 xor，最后不足一块的尾段全部 xor。

因此需要处理的范围是配置给出的，不能直接把整个 .so 异或一遍。

xor 的字节来自传入的 seed。0x156904 右移 16 位，0x156930 广播字节，0x156954 执行向量异或。简化后的取值规则如下，旁边的连续 xor 函数 sub_156844 也是同样的规则：

画一下 seed 和区域处理的关系。下面只画当前记录使用的大区段、模式 1 分支：配置决定处理哪里，seed 决定用什么密钥；AES 和 xor 作用于不同的子区间。

flowchart TD S["32 位 seed：0xba981955<br/>计算过程暂不展开"] C["区域配置 + 模块基址<br/>起点、长度、模式"] --> F["sub_13FEE0<br/>大区段，模式 1"] S -->|W2 参数| F F --> R["调整起点 P<br/>P = 起点 + 0x2000 - 起点低 12 位"] S --> K["按 %08x%08x 将 seed 拼接两次<br/>得到 16 字节 ASCII AES 密钥"] S --> X["k = seed 的第 16–23 位<br/>若为 0，改用 0x87"] R --> A["sub_13E57C：AES-CBC<br/>处理 P 到 P+0x4000<br/>每 0x800 字节独立重置 IV"] K --> A V["固定 IV"] --> A A --> Q["sub_156870：周期 xor<br/>从 P+0x10000 开始<br/>每完整 0x10000 块处理前 0x4000<br/>不足一块的尾段全部处理"] X --> Q Q --> O["完成该区域的这轮解码<br/>其余子区间保持原样"]

这里的箭头表示 AES 处理完后继续处理后面的 xor 区间，不是把同一段数据先 AES 再 xor。代入 seed 0xba981955，xor 字节为 0x98，AES 密钥为 16 字节 ASCII 字符串 ba981955ba981955。

metadata 解密#

解密 libil2cpp.so 后，继续分析 metadata 的加载路径，并结合 libanort.so 确定文件的解密方式。代码段的 0x98 和 metadata 的 0x66 要分开看。

0x54389BC 会经过文件映射路径读取数据。另一边，libanort 中的 sub_152594 参数形式与 mmap 一致，它先检查文件头，匹配 0x12724394 后解密，否则回到普通 mmap。

我们的 metadata 前四字节是 94 43 72 12，按小端序读取就是这个标记。不过，两边具体如何通过 hook 接上，安装过程还没完全追完，先保留这个缺口。

metadata 的 seed 倒是很直接：在 0x15271C 附近准备 0xD96603C0，于 0x15272C 调用 sub_156638。

最开始对 xor 0x66 的猜测得到验证。AES 密钥也来自同一个参数，在 0x1567A4 用 %08x%08x 拼接两次，得到 16 字节 ASCII：

IV 位于 libanort.so:0x190060。0x13E448 将 0x4000 字节拆成八块，后续经 0x13E37C、0x13F25C 做 AES-128-CBC，每块重新设置密钥和 IV，无填充。

整理得到文件解密规则，下面均为文件偏移：

  1. [8, 0x1000)：xor 0x66。
  2. [0x1000, 0x5000)：AES-128-CBC，使用上述密钥和 IV，每 0x800 字节重置一次。
  3. 从 0x11000 开始，每个完整 0x10000 字节块的前 0x4000 字节 xor 0x66。
  4. 最后不足 0x10000 字节的尾段全部 xor 0x66，这里不要漏掉。
  5. 按加载器行为清零 [0,4) 和 [5,8)，保留偏移 4 的 0x18。
