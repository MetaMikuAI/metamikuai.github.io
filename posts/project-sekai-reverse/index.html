  2. 比对 apk 中解包出的 metadata，删除多余的 00 字节
  3. 复原 FF FF FF 7F -> D0 39 1E 00
  4. 复原 18 -> 1B
  5. 复原 00 00 00 00 -> AF 1B B1 FA
  6. 删除头 8 字节，即使 AF 1B B1 FA 位于文件开头

分析 JWT (基本完成)#

  1. 观察到流量中有大量 JWT 以 X-Session-Token credential sessionToken signature param 等处出现
  2. 除 param 外，所有 jwt 均包含用户的 userId 和一个未知含义的 uuid
  3. 所有 jwt 的签名密钥均未知 (也有可能是我菜，尝试 frida hook 了一些哈希函数无果，大概本地完全不验签，只有服务器会验签)
  4. 所有 jwt 的 header 均为：

速写了一段用于 JWT 分析（加解密函数略）

  1. 启动游戏时会发送第一个请求 GET /api/system 不携带 X-Session-Token
  2. 然后访问 /api/user/<userId>/auth?refreshUpdatedResources=False 并在 payload 中携带 credential，每次登录的时候都会携带该 credential 不变 (该 credential 与用户绑定，所谓更新丢账号应该就是丢的它)，服务端返回 sessionToken
  3. 在此之后，客户端的所有请求都需携带该 sessionToken
  4. 服务端除 /api/system 和 /api/information 外，都需要返回新的 sessionToken，客户端收到后更新 sessionToken，并在下次请求中携带新的 sessionToken（平时网络不好导致卡退到主界面大概就是因为这个不同步了吧）保证了前向安全性
  5. 该 credential 不随 重新登录 或 设置引继码 而变，但是会在确认继承引继码时接收服务器分发的新的 credential
  6. userRegistration 的 signature 似乎永远不变
  7. 注：jwt 的签名密钥无从得知，如果需要在官方服务器和个人服务器之间反复测试的话，个人服务器不得分发新的 credential （但是可以重放），以免账号丢失（20260616 补充：SNA 和 引继码相关 jwt 还是可以在客户端审计到的）

防护意见#

在修改 API-URL 这一段攻击链中，主要涉及以下几个方面的问题：

  1. global-metadata.dat 解密过于简单且可逆，导致攻击者可以自由解密和重加密
  2. libil2cpp.so 明文存于 apk 中，易于解密、审计和篡改
  3. apk 缺少强签名校验，很容易被篡改

对此我有几个不成熟的修复方案仅供参考，

  1. 最简单最粗暴的方法，给 apk 加壳加强签名校验，篡改后无法安装
  2. 使用非对称加密来保护 global-metadata.dat，使攻击者无法重加密，将弱点转移至保护较短的、更便于隐藏和混淆的解密公钥上
  3. 关键常量字符串混淆或拼接，增加攻击者的审计难度
  4. 移除对回环地址的白名单
  5. 对代码进行混淆，避免攻击者轻易找到切入点（我总记得以前是有混淆的来着？）
  6. 移除 url_config.json，将渠道服和非渠道服的差异化配置放在代码中进行编译时区分，而不是放在外部文件中
  7. 使用极短的域名来获取实际 API 地址，限制攻击者的篡改范围
  8. 使用自行签发的证书，拒绝其他包括根证书在内的证书，增加攻击者的测试难度
  9. 参考其他游戏，如「明⚪⚪舟」，有极为严苛的环境检查，从开始即限制攻击者的抓包分析和修改测试
  10. 现有逻辑是极为标准的 Unity il2cpp 游戏模型，可以考虑对敏感逻辑进行特殊化处理，减少同质化攻击面

在 AI Agent 飞速发展的今天，想快速审计一个 il2cpp 游戏已经不是难事，如果能配合地用好工具，一定能达到事半功倍的效果。这里将首先分享一下个人为此准备的一套工具和工作流，然后按各个功能模块进行粗浅地分析，以供大家参考。这部分可能有 AI 生成总结的部分（因为 AI 真的比我总结的更高效、更准确、更有价值），此类内容会在所属小节开头进行标注。

逆向工具#

在去年，我可能会说，下面的工具只需配置一部分即可。但是在现在，接下来的每一个工具都是我经过大量实践总结出的一套模式，如果以后有进步也会同步进行更新。

  • 010-Editor：用于查看文件的十六进制，有助于恢复 global-metadata.dat，也可使用其他工具替代。

  • Il2CppDumper：il2cpp 逆向最权威的工具，用于解析 global-metadata.dat 并导出字符串表以及 DummyDll 等重要产物。

  • dnSpy：用于粗略审计 DummyDll/*.dll，导出为桩代码项目可供 AI Agent 快速审计。

  • IDA Pro：用于对 libil2cpp.so 进行反汇编分析，并在必要时进行动态调试。对于 il2cpp 游戏，IDA 是理解底层执行逻辑的重要工具。

  • IDA-Pro-MCP：该插件允许AI Agent通过MCP接口访问IDA数据库，可用于辅助定位函数、理解控制流或加速分析过程。

逆向分析准备#

  1. 恢复 global-metadata.dat，老生常谈的话题了，应该非常简单了吧）大家都会了。
  2. 找到 libil2cpp.so，一般在 安装包里的 lib/arm64-v8a/libil2cpp.so
  3. 使用 Il2CppDumper 读取 global-metadata.dat 和 libil2cpp.so，等待一会可以得到一些产物。如果报错，检查是否是二者有未解开的加密或损坏。
  4. 将 Il2CppDumper 生成的 DummyDll/Assembly-CSharp.dll 导入dnSpy。通过该文件，我们可以较为直观地查看游戏逻辑中的类定义、字段名称以及方法签名，并定位其虚拟地址。
  5. 在 dnSpy 中选中 Assembly-CSharp.dll，并通过 文件 > 导出到工程 将整个项目进行导出，导出的代码不含具体逻辑，只含结构，以供 AI Agent 进行标准的参考。
  6. 使用 IDA Pro 打开 libil2cpp.so，等待其完成初始自动分析（首次加载耗时会非常长，建议导入后直接睡到天明）。

  9. 关闭 IDA，切记勾选 Collect garbage 而不要勾选 Don't SAVE the database，重新备份产物 libil2cpp.so.i64。
  10. 为 IDA 安装 IDA Pro MCP
  11. 安装 skill：IL2cpp-to-csharp-skill
  12. 打开 IDA，启用 IDA Pro MCP，将桩代码目录和 Il2CppDumper 的产物 stringliteral.json 路径提供给 Agent，即可让 Agent 开始逆向分析。

将同一版本的资料集中整理，并在 README 中注明来源、用途和阅读顺序；经过解密或修补的文件也应标明。以日服 6.8.1 为例：

静态分析#

stubs、pseudocode 和 cpp2il-cs 使用相同的“程序集 / 命名空间 / 类型”路径，便于对照：

先用 stubs 确认结构，再用 pseudocode 分析逻辑，需要时查阅 dump。Cpp2IL 的结果可能有错误或缺失，存在冲突时，应回到反汇编和原始数据核对。

给 AI Agent 使用时，也应明确这个顺序，要求结论附上方法或地址，不确定之处保留疑问，不猜写缺失逻辑。已有完整伪代码时，无需每次启动 IDA。

C# 之外的分析#

本游戏本文涉及的主要业务逻辑，以 C# 对应的 IL2CPP 代码为主要审计对象即可。其他游戏的加密、登录 SDK 或保护逻辑可能分布在不同层，还需补充：

  • Java 层：使用 JADX 导出 APK 中的 Java 反编译代码，查看应用入口、SDK 调用和 JNI 接口。
  • Native 层：保留相关 .so，使用 IDA、Ghidra 等工具分析导出函数、调用关系和具体实现。

遇到跨层调用时，应沿着 C#、Java 与 Native 之间的实际调用关系继续追踪。

动态验证（进阶）#

基本流程是：静态定位 → 进入对应场景 → 记录状态与调用 → 对照分析结果。必要时再临时修改行为，观察实际效果，结束后撤销修改。

  1. 游戏直接闪退：FusionCore 误将 global-metadata.dat 当明文读取而崩溃，这在 Add global metadata override during bootstrap 被解决，请将解密后的 global-metadata.dat 放到 /sdcard/FusionCore/<包名>/ 下
  2. 游戏可以正常加载，但有关 Google Play 的一些图标等资源加载错误：FusionCore 包装后导致和 Google Play 通信的一些问题，这在 Fix launcher context wrapping for game resources 被修复。
  3. 游戏可以正常加载，但是只能在标题页，点击标题无法登录游戏：与第二条类似的问题，这在 Fix Unity launch context and Firebase discovery 中被修复。

游戏正常加载，甚至可以直接带起来 UnityExplorer

BepInEx 直接注入（推荐的方案）#

20260829 记

All-Of-Us-Mods/FusionCore 算是证明了 Android Unity IL2CPP 跑 BepInEx 的可行性，但它本身有不少问题，至少截止到上次整理这块代码时，遇到过如下问题：

  1. Firebase 异常，无法正常使用 Google Play 相关服务。
  2. 要外置一个 app、再镜像一份游戏，不太优雅。
  3. BepInEx 的更新不太方便。
  4. 我不喜欢 Java。

所以干脆自己改了一套。参考 All-Of-Us-Mods/FusionCore 和我的 fork 版本 MetaMikuAI/FusionCore，对官方 BepInEx 工具链做了 Android 适配，拆成四个仓库：

  1. BepInEx-Android-Bootstrap：原生启动加载器，编译产物 libmodbootstrap.so。
  2. Il2CppInterop-Android：arm64 适配的 Il2CppInterop，含 Android return-buffer detour 支持。
  3. BepInEx-Android：BepInEx 核心。注意它引用的 Il2CppInterop 必须换成上面仓库的本地工程引用，直接用 NuGet 包会因接口不匹配报 CS0535。
  4. BepInEx-Android-Injector：APK 装配脚本。

编译方面：安装 Android NDK 后，让 AI 读一下就能编出前三个（BepInEx-Android 和 Il2CppInterop-Android 需要 .NET SDK）；另外还需要编译 BepInEx/Dobby 得到 libdobby.so。

加载原理（by dsv4f）#

装配阶段（injector）：解密 metadata → 组装 assets/mod（BepInEx 核心 + dotnet + 解密 metadata）+ lib/arm64-v8a/*.so（bootstrap/dobby/coreclr 等）+ 新增 classes dex → smali 注入一行 Bootstrap.load()。

启动阶段接力链：

关键设计：

  • 注入点选 NativeLoader.load() 成功后：libil2cpp.so 已加载（能 dlsym），且 il2cpp_init 未调用（来得及 hook）
  • payload 放 assets：AAssetManager 读 APK 资产免权限；解压到外部存储是因为运行时要写（interop/日志）
  • 运行时 .dex 单独成 classesN.dex：Android 只认 dex 里的 Java 类
  • detour 统一经 modbootstrap 中转：托管层调 mod_dobby_prepare/commit/destroy，bootstrap 内部 dlopen libdobby.so，并管理 ARM64 return-buffer 桥（大结构体返回值经 x8 返回，普通 hook 会丢，mmap 桥代码保存/恢复）
  • smali 只是扳机：真正的加载逻辑全在 libmodbootstrap.so

逆向重建#

开篇#

20261029 记

终于在今天，可以开始进入真正的终章——逆向重建。

资源、shader 等暂时基于 AssetRipper Premium，代码基于自研反编译工具 MetaMikuAI/Cpp2CS。

重建策略是，一条线基于 AssetRipper 和 Cpp2CS 的导出开始组装，如有缺口则记录并手动修补；另一条线基于记录的缺口，定向修补 Cpp2CS 工具。

两者结合，可以自主推进逆向的进行。（除了比较费 token，一天大概花费 5~10 亿 的 astra token）

Cpp2CS#

20261029 记

介绍下 MetaMikuAI/Cpp2CS，wip 的 il2cpp arm64 的反编译器。目前整体看效果比 SamboyCoding/Cpp2IL 和我同群u们优化的 MetaMikuAI/Cpp2IL要强很多。
